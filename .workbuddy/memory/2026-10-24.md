## unitPrice 进 payload：四选项决策的解释（回答用户"以上是什么意思"）

核实结论：
- `StableOrderJson.kt:175-186`：`productName`/`unitPrice` 都是条件写（非 null 才写，目前只有手动改价时 unitPrice 有值）；`barcode/name/quantity/amount` 固定写。
- `OrderPayloadIndex.kt:365`：解析侧只读 barcode/name/quantity/amount —— "unitPrice 只写不读"属实。
- `StableOrderJsonTest.kt:499-533`：两条 SHA-256 跨语言断言用的 `OrderLine` 是四参构造（unitPrice=null），
  所以一旦改无条件写，224B/218B 字节数、两条 SHA、statusValueByteIndex 全部失效，期望值必须由仓库外
  `test_all.py` 的 `jstr()`（json.dumps ensure_ascii=False, separators=(",",":")）独立重算。
  红线：禁止只用 Kotlin 重算期望值 —— 跨语言验证会退化成自己跟自己比；中文多字节、码点 vs 字节下标
  正是这两个测试存在的理由（测试类注释已自记该隐患）。
- 字节代价：每行约 +20 字节（`,"unitPrice":"95.00"`）；`estimateItemBytes` 已含 unitPrice 估位，
  拆单决策公式不用改，但按旧字节标定的阈值类测试要重跑；服务端纯增量兼容（老单缺字段=无折扣行）。
- 旁表 `outbox_price_snapshot` 方案否决：只在开单设备存在、换机器打印即空、上传后进不了
  order_index/order_item_index 镜像层 —— 违背"任何机器可打印任何单"。

给出的建议：A（改 payload + 同步 Python 参照）与 B（先跑通 ByteIdentityGateTest）合并成一条顺序：
① 搭真服务端（tls :8443 + 同机 Redis + 磁盘目录可读）→ ② 跑绿字节门记录改动前 SHA 基线 →
③ 同一次改动 unitPrice 改无条件写（productName 是否同船单独评估，中文字段字节贵）→
④ 仓库外 Python jstr() 独立重算两条 SHA → ⑤ 同 PR 重跑，门保持绿才算完。
ByteIdentityGateTest 欠账背景：需真服务端否则 assumeTrue 整体 skip，"门不过 P7 后 UI 不许动"的线已被越过。

待用户拍板（延续）：P6b AdoptionTx 选哪个方案（我建议①编排器+测试先行，B 类 6 张降级为断言为空）、

## 追问："没有老订单数据，岂不是没有这些担忧？"

答：只对一半。真正被消除的只有"老单缺 unitPrice 的退化/迁移/发版协调"这一半；
最硬的两条（两条 SHA-256 断言必须由 Python 参照重算、ByteIdentityGateTest 欠账）跟老数据毫无关系。
另外每行 +20 字节的物理成本、拆单阈值测试重标定也都还在。

关键纠正 —— "老数据"有四处藏身，第二处最容易被忽略：
① 服务器订单文件（追加写、补丁只能等长覆写，字节永久定死，擦不掉）；
② **本地 outbox 的 payload BLOB：enqueue 时就序列化冻结**（`OrderGroupAssembler.kt:227` 调 serialize，
   `OutboxUploader.kt:315` 注释明说"payload 是 enqueue 时生成且当时自检过的字节"），
   改序列化器后未上传的存量行就是旧格式死字节 —— 所以"没上传过单"不等于"没有旧格式字节"；
③ 镜像层 order_index/order_item_index（可由 FULL 重建）；④ 测试账户 alice/gate2028（清库即可）。

净结论：没数据 = 现在改最便宜 → 更应趁现在把格式一次定死（unitPrice 无条件写，productName 可一并决定），
不必留"新旧两种字节形态"分支、不必写 Room migration。但序列化器里只要还留条件写路径，
就会继续造出"新形态老单"，所以 unitPrice 必须无条件写、别留 null 分支。
确认是否真无数据的方法：查 outbox 行数 + 服务器目录是否已有文件 + 测试账户。

## 追问：字节门欠账是什么意思 / 为何不直接拿服务器订单文件算 SHA

字节门 = ByteIdentityGateTest（方案 §7.2）：本地镜像 vs 服务端磁盘文件**逐字节 diff**（含 4 字节版本头）。
之所以是"门"：等长覆写打错偏移时文件长度不变、checksum 自洽、`file_state` 游标对得上，
服务端 WAL/checksum **检测不出语义破坏**；此后每次取消/改备注都静默打在**别的订单**字节上、不可恢复；
`orderfile:checksum:<fileId>` 客户端读不到（无接口）。需要真 service1（tls :8443）+ 同机 Redis +
磁盘目录（默认 `service1/data/orders`，`-Ds1.data` 覆盖）；没跑则 `assumeTrue` 整体 skip
→ 报告绿但什么都没验证 = 假绿 = 欠账。"门不过 P7 后 UI 不许动"（方案 §九）已被越过。

三条证据通路（关键区分）：
① 离线 SHA 交叉验证 StableOrderJsonTest：Kotlin vs Python jstr 两个独立实现撞出同一 SHA，毫秒级、每次单测都跑；
② 真门：上传后读服务器磁盘 diff（端到端，当前 skip）；
③ **FULL 接口回读 = 自证**（类注释原话：FULL 是同一份字节，那就成了自证），不算证据。

为什么不能拿"服务器订单文件"当期望值来源（规范 vs 历史）：
a) unitPrice 是新字段，历史文件里没有样本，根本算不出来；规范侧 Python jstr（跑通 161 条契约断言）可以先加字段再算；
b) 服务器照收错字节 —— 往返一致 ≠ 形状正确；
c) 字节门要完整环境 + 登录限速（5/60 且 maxBurst=1 → 严格 12 秒一次，整个类只登一次），是最后确认而非日常反馈。
"自己跟自己比"的退化：期望值若由 Kotlin 反填，序列化器怎么坏测试都绿。
技术坑：读回后靠 uuidOffset/statusOffset 字节下标定位，Python 侧 `rindex` 用码点下标，中文 item 差 8 字节（测试注释已记）。

## 核实"最大缺口"：OutboxStore.enqueue 无生产调用方

- 属实：全仓 `.enqueue(` 的调用方**只有三个测试**（OutboxStoreTest:103 / RoomMirrorStateStoreTest:677 /
  OutboxUploaderTest:180）；生产代码里 `enqueue` 只出现在注释（Entities.kt:423、OrderFileDao.kt:360）。
- 但读取侧与动作侧**已接线**：ServiceLocator:428 OutboxStore、:353 OutboxUploader、:497 OrderRepository；
  ui/orders/OrdersViewModel:61 持 OrderRepository；OrderRepository 有 uploadSelected→uploader.uploadOne、
  discard→outbox.discard、refreshBlocked→outbox.refreshBlocked，**唯独没有 enqueue 的转发**。
  所以准确说法是"链条是通的，只缺入口匝道"，不是"零交集"。
- 开单页 ui/order/OrderViewModel 三个出口全是文件/SP（触发点在 OrderScreen.kt:134 / :149）：
  保存 → PendingOrderStorage 写 `filesDir/PendingOrders/*.json`；
  打印（成交）→ OrderHistoryStorage 写 `filesDir/Orders/<年/月/日>/*.json` + 打小票；
  购物车草稿 → OrderStorage 写 SharedPreferences `order_storage`。
- **别修错地方**：`filesDir/PendingOrders` 是明确产品决定（MainActivity.kt:63：待开单是本机草稿，换设备不需要看到）；
  `filesDir/Orders` 旧历史页是"临时保留，P8 迁移向导做完再摘掉"（MainActivity.kt:74）。都不是缺口。
  真正缺口 = 成交（打印）时没有任何一步 enqueue 进 outbox。
- 后果：Orders 页在真机上看不到本机新开的单，只能看到别的设备 SSE 推来 / FULL 拉来的；上传链与统计搬桶空转。
- 补线三步：① OrderRepository 加 `submit(req, hasBoxSize)` 薄转发 enqueue（UI 不直接碰 OutboxStore）；
  ② 打印时**先 enqueue 再打小票**（数据比纸重要，enqueue 是 DB 事务、打印是外设 I/O）；
  ③ hasBoxSize 由调用方查商品表传入（OutboxStore 故意不持 ProductDao，见 OrderRepository:155 注释）。
- 待用户确认：成交的语义入口是否就是"打印"按钮（目前它是唯一出口）。

## 解读 OrderMode / CurrentOrderMode / ModeSwitchBar / 旧历史页

- `ui/OrderMode.kt:33`：SALE（销售）= B 类文件，计营收扣库存；PURCHASE（进货）= A 类文件，
  不计营收不动库存，且不算价格/不显示总额/小票不印金额（服务端不存买入价，本地 price 是卖出价）。
  ⚠ 自采（打印拿去别店买/直接入库，纯本地）与向总部下单（A 类上传）当前**共用一个 PURCHASE**，
  是否拆两个模式等 P11 库存联动定。
- `CurrentOrderMode`（:61）进程级单例（同 `db.CurrentStore` 理由：手工装配无 DI），
  **刻意不持久化**，冷启动回 SALE —— 防"进货模式跨天留着，第二天开出的 A 类单不计营收凭空消失"。
- `ModeSwitchBar`（:100）三页都放（开单 MainActivity:195 / 待开单 :276 / 旧历史 :290），
  理由是历史页同时列两种单、没开关没法按模式筛；进货模式下吸顶变色 + 红字提示。
- 旧历史页 `LegacyHistory`（MainActivity:78）：读 `filesDir/Orders/<年/月/日>/*.json`，
  **临时保留**——用户过去几年的订单只在这些文件里，P8 迁移向导做完前删掉就打不开了。
  入口在「我的」页。`Orders` 新页读 order_index + outbox，现在空的（缺 enqueue）→ 两套账并存。

## 顺带发现的两个隐患（旧历史相关，迁移前要先处理）

1. `OrderHistoryRecord(id, createdAt, totalPrice, items)` **没有 mode 字段**
   （`data/OrderHistoryStorage.kt:20`）。后果：旧历史页那根 ModeSwitchBar 筛不了旧数据；
   更严重的是 P8 迁移时无从判断哪笔是销售、哪笔是进货 —— 而服务端是 A/B 两类完全不同的文件。
2. `OrderViewModel.saveOrderToHistory()`（:305）写 `totalPrice = totalPrice.toPlainString()`，
   而 `totalPrice`（:44）= `Σ item.subtotal`，**无任何模式判断**，subtotal 基于卖出价。
   即：**进货模式下写进历史文件的金额是卖出价算的**，正是 OrderMode.kt:43 注释警告的"编数字"。
   将来 P8 若把它搬进 `order_index.totalCents` 会污染统计。
建议（都很便宜）：① 给 OrderHistoryRecord 补 `mode` 字段，老文件按"无标记=销售"处理；
② 进货模式下历史文件写 totalPrice="0"，别把编出来的数字落盘。
