- 回答"允许修改上传内容以减少表/多上传商品名称"（配 1 表）。先校正：item 的 name 现在就在传（StableOrderJson 固定写 barcode/name/quantity/amount，A 类另带 productName；OrderPayloadIndex.parseItems 读 content 的 name 建 order_item_index）。product_tombstone 只因"补传历史单/FULL 恢复旧单可能没有 name"而存在。评估结论：删 tombstone 的正确做法是服务端一次性 name 回填（数据迁移，非协议能力；需一次强制 FULL 重建）；**否决内容改写 API**——偏移是绝对字节位置，变长改写让它之后全部失效，镜像/补丁/FULL 三层连锁重写，为一张表改架构是负收益。收益最大的服务端杠杆其实是 /add 的 uuid 幂等（重复添加返回已存在），可根除重复扣库存并大幅简化 outbox 状态机。name 已在传，再加字段（如分类）是拿 413 拆单概率换表数，不划算。

- 回答"order_outbox 状态机如何实现幂等"（配 1 图：七道闸门）。核心设计：所有防重判据都压在数据库返回值上，不靠调用方记 boolean（"进程在两步之间被杀时 boolean 已经不在了"——RoomMirrorStateStore 注释原话）。七道闸门：① uuid 客户端生成绝不复用；② takeOff CAS（UPDATE WHERE state='READY'，只有返回 1 的能发，且先落盘后发请求）；③ 未知结果绝不盲发（留 IN_FLIGHT）；④ insertOrderIndex 用 IGNORE + rowId=-1 判"索引行已在→贡献已加过→直接返回"（FILE 桶侧）；⑤ markOutboxPromoted 带 state NOT IN ('DRAFT','PROMOTED')，只有第一次返回 1（OUTBOX 桶侧，减桶用 enqueue 时同一个 OutboxContribution.of 同一份字节保证净值零）；⑥ PROMOTED 行永不删（"已上传过"的唯一凭据）；⑦ recoverInFlight 重推前必须取证（同步 fileId + 查 order_index）。关键架构决定：搬桶放在 RoomMirrorStateStore 而非上传器——"服务器已经有了"有三条来路（/add 响应、SSE 回声、FULL），放上传器会让后两条把钱永久留在 OUTBOX 桶且不报错。恢复重发不走 takeOff（CAS 要求 READY 会返回 null 让单子卡死），直接发。诚实边界：服务端无去重，同一 uuid 两台设备各传一次客户端无机制发现；未知窗口闭合依赖同步成功。
